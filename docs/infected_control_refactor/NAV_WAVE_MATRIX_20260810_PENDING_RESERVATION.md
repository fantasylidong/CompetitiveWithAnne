# 2026-08-10 Pending Nav 占位全官图测试

## 结论

本轮在云 58 的 `anne1` 容器上，以最终部署的 Linux 扩展和
`infected_control.smx` 跑完 57 张官图、每 5% 进度一次的 1083 个场景。
所有场景都实际生成 12/12，共生成 12996 只特感；服务器侧完整波耗时全部
低于 3 秒。

Pending Nav 占位符合当前约定：

- 同一个 NavID 内，请求点距离小于 120u 时暂时排除；大于等于 120u 可以复用。
- 不同 NavID 按点位距离暂时排除，基础半径 80u，并随配置的特感上限缩小。
  本次 `l4d_infected_limit=12` 时半径约为 68.27u。
- 实体确认成功后，记录实际落点并使用原有 3 秒分散保护；12 特配置下半径约为
  50.67u。
- 以上距离均为三维直线距离，不是 Nav 中心距离或有向路径距离。

对 63858 对同时处于 pending 状态的有向 Nav 请求回放检查后，阈值违规为 0：
其中同 NavID 990 对，全部大于等于 120u；不同 NavID 62868 对，全部满足当时的
动态分散半径。

## 密集生成分析

过滤器累计命中：同 Nav pending 175313 次、不同 Nav pending 点距 199807 次、
已确认落点分散 10412 次、Nav 冷却 5534 次。说明修复确实在单帧连续生成时
大量拦截了尚未确认的重复候选，而不是依赖 0.5 秒成功后冷却。

有向 Nav 到有向 Nav 的完全重合为 0。仍有 9 对完全相同的实际落点，全部包含
Director/API 直出，共出现在 4 个场景。这是 API 直出绕过分散检查的直接结果，
不属于 pending Nav 占位遗漏。若以后要消除这 9 对，只需给 API 增加内存点距
去重和重新请求，不需要恢复路径、距离、可见性、stuck 或伤害区域检查；但这会
改变当时“API 返回点直接生成”的契约，本轮未擅自修改。

## 动态 Nav 稳定性

首轮测试在 `c5m5_bridge` 95% 触发了 SRCDS 进程退出。原因是电梯移动期间扩展
读取了引擎正在变化的 Nav 连接数据。扩展已调整为只在 Nav area 列表有效且动态
载体静止时遍历连接；修复后该场景连续重试 3 次均为 12/12，完整波耗时
531-594ms，容器 `RestartCount` 始终为 0。最终 1083 场景矩阵未再出现进程退出。
